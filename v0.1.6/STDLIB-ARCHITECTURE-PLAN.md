# Hardware Script v0.1.6 Standard Library Architecture

**Version**: 0.1.6  
**Focus**: The Foundry - Standard Library as the ISA of Physical Reality  
**Status**: Implementation Plan  
**Philosophy**: "The compiler is intentionally dumb. The library defines physical reality."

---

## Executive Summary

This is a **pivotal moment** in Hardware Script's evolution. By establishing the Standard Library (Stdlib) architecture in v0.1.6, we are transitioning from "building a compiler" to "designing an ecosystem."

**Core Insight**: Because the compiler is intentionally "dumb" and relies on the library to define physical reality, the Standard Library isn't just a collection of parts—it is the **Instruction Set Architecture (ISA) of the physical world**.

**Key Principles**:
1. **Large files are better** - The compiler's Symbol Table is O(1). One `components.hw` file with 1,000 resistors is faster than 1,000 separate files.
2. **Organize by Physical Domain** - Group by material/process, not arbitrary categories.
3. **Recursive Comptime Generics** - Use the new ArrayIndex::Arithmetic to stress-test the compiler.
4. **The Boundary Law** - Properties use `:`, calculation logic uses `=`.
5. **Foolproof Testing** - If we can define a 1024-bit adder with a loop, the compiler is production-ready.

---

## 1. The "Foundry" Folder Structure

We organize the library by **Physical Domain**. This mirrors how hardware engineers think about their designs.

### Proposed Structure (`hwc/stdlib/`)

```
hwc/stdlib/
├── primitives/          # Ships inside the compiler binary
│   └── units.hw         # Fundamental math and SI relationships (V, A, Ω, m)
│
├── materials/           # The "Atoms"
│   ├── conductors.hw    # Copper, Gold, Aluminum, Solder
│   ├── insulators.hw    # FR4, Rogers, Polyimide, Air
│   └── semiconductors.hw # Silicon, GaN, P-type/N-type
│
├── logic/               # The "Targets" for behavioral synthesis
│   ├── gates.hw         # NAND, NOR, XOR (Atomic level)
│   ├── arithmetic.hw    # Adders, Multipliers, Shifters
│   └── memory.hw        # D-Flip-Flops, SRAM cells, Registers
│
├── routing/             # Geometric strategies
│   └── patterns.hw      # Trombone, Serpentine, Zigzag math
│
└── components/          # Standard footprints
    ├── passives.hw      # SMD Resistors/Capacitors (0402, 0603, 0805)
    └── ics/             # Folders for specific standard packages (QFN, BGA)
```

### Why This Structure?

**Performance**: The compiler's symbol table is O(1) lookup. Parsing one large file is faster than opening 1,000 tiny files.

**Modularity**: If I'm building a PCB, I only import `@std/materials/conductors`. I don't need `semiconductors.hw`.

**Logical Grouping**: Keep logic gates in one file so the synthesizer has a fast "shopping list" when it unrolls your code.

## 2. Making it "Foolproof": The Stress-Test Strategy

To catch bugs in the new "God-Tier" logic and index math, we will write the Stdlib using **Recursive Comptime Generics**.

### The Test

Instead of writing an 8-bit adder and a 16-bit adder separately, we write **one N-bit Generic Adder** that uses the new `ArrayIndex::Arithmetic` to build itself.

**If the compiler can't handle a 1024-bit adder generated by a loop, we've found a gap.**

This approach:
- Validates the new array indexing logic
- Stress-tests the recursive MuxTree generator
- Proves the compiler can handle real-world parametric designs
- Provides a canonical example for users

## 4. Catching the "Gaps": The Logic Soul

The biggest gap we identified was the **Recursive MuxTree**. To fix this, we will implement `gates.hw` using the `match` keyword.

### File: `hwc/stdlib/logic/gates.hw`

```hw
module AndGate:
    pins: [input A, input B, output Out]
    logic:
        # Single (=) for both comparison and assignment in logic blocks
        Out = match [A, B]:
            [1, 1]: 1
            else: 0

module OrGate:
    pins: [input A, input B, output Out]
    logic:
        Out = match [A, B]:
            [0, 0]: 0
            else: 1

module XorGate:
    pins: [input A, input B, output Out]
    logic:
        Out = match [A, B]:
            [0, 0]: 0
            [1, 1]: 0
            else: 1

module NotGate:
    pins: [input In, output Out]
    logic:
        Out = not In

module Mux2to1:
    pins: [input In[2], input Sel, output Out]
    logic:
        Out = match Sel:
            0: In[0]
            1: In[1]

module Mux4to1:
    pins: [input In[4], input Sel[2], output Out]
    logic:
        # This will trigger the new Recursive MuxTree generator
        Out = match Sel:
            0: In[0]
            1: In[1]
            2: In[2]
            3: In[3]
```

**Key Features**:
- Uses `match` for truth table definitions
- Single `=` for assignment (v0.1.6 syntax)
- Array indexing with `In[0]`, `In[1]`
- Mux4to1 tests the recursive MuxTree logic

## 5. The "Foolproof" Test: Arithmetic Library

This is where we **stress-test the compiler**. If we can define a 64-bit Ripple Carry Adder using `for i in 0..N` and `In[i-1]`, and it compiles to a perfect 3D voxel grid, then Hardware Script is officially ready for production.

### File: `hwc/stdlib/logic/arithmetic.hw`

```hw
## Standard Library v0.1.6 - Arithmetic Primitives
## Stress-tests the compiler's recursive logic and array indexing

module HalfAdder:
    pins: [input A, input B, output Sum, output Carry]
    logic:
        Sum = A xor B
        Carry = A and B

module FullAdder:
    pins: [input A, input B, input Cin, output Sum, output Cout]
    logic:
        Sum = A xor B xor Cin
        Cout = (A and B) or (Cin and (A xor B))

# Generic N-bit Ripple Carry Adder
# This is the CRITICAL test for ArrayIndex::Arithmetic
module RippleCarryAdder:
    params:
        width: 8  # Default to 8-bit, but can be overridden
    
    pins: [input A[width], input B[width], input Cin, output Sum[width], output Cout]
    
    logic:
        # Internal carry chain
        reg carry[width + 1]
        carry[0] = Cin
        
        # Generate full adders for each bit
        for i in 0..width:
            Sum[i] = A[i] xor B[i] xor carry[i]
            carry[i + 1] = (A[i] and B[i]) or (carry[i] and (A[i] xor B[i]))
        
        Cout = carry[width]

# 8-bit Adder (concrete instantiation)
module Adder8:
    pins: [input A[8], input B[8], input Cin, output Sum[8], output Cout]
    
    instance:
        adder: RippleCarryAdder(width: 8)
    
    bindings:
        adder.A = A
        adder.B = B
        adder.Cin = Cin
        Sum = adder.Sum
        Cout = adder.Cout

# 16-bit Adder (concrete instantiation)
module Adder16:
    pins: [input A[16], input B[16], input Cin, output Sum[16], output Cout]
    
    instance:
        adder: RippleCarryAdder(width: 16)
    
    bindings:
        adder.A = A
        adder.B = B
        adder.Cin = Cin
        Sum = adder.Sum
        Cout = adder.Cout

# 64-bit Adder (stress test)
module Adder64:
    pins: [input A[64], input B[64], input Cin, output Sum[64], output Cout]
    
    instance:
        adder: RippleCarryAdder(width: 64)
    
    bindings:
        adder.A = A
        adder.B = B
        adder.Cin = Cin
        Sum = adder.Sum
        Cout = adder.Cout
```

**Key Features**:
- Generic `RippleCarryAdder` with `width` parameter
- Uses `for i in 0..width` for comptime stamping
- Array indexing with arithmetic: `carry[i + 1]`
- Concrete instantiations (8-bit, 16-bit, 64-bit)
- If this compiles, the compiler is production-ready

## 7. Implementation Roadmap

### Phase 1: Compiler Enhancements (Prerequisites)

These compiler features must be implemented before the stdlib can be written:

1. **Recursive MuxTree Generator** (Task A3b dependency)
   - Implement recursive match statement expansion
   - Handle arbitrary-width multiplexers
   - Generate optimal tree structure

2. **Saturating Index Math** (Arithmetic library dependency)
   - Implement `ArrayIndex::Arithmetic` for `i + 1`, `i - 1`
   - Add bounds checking and saturation
   - Enable `for i in 0..N` with array access

3. **Parametric Module Support** (Generic adder dependency)
   - Implement `params:` block parsing
   - Support parameter overrides in instantiation
   - Enable comptime evaluation of parameters

### Phase 2: Stdlib Structure Creation

1. **Create folder structure**
   ```bash
   mkdir -p hwc/stdlib/primitives
   mkdir -p hwc/stdlib/materials
   mkdir -p hwc/stdlib/logic
   mkdir -p hwc/stdlib/routing
   mkdir -p hwc/stdlib/components/ics
   ```

2. **Move existing materials**
   - Split `hwc/stdlib/materials.hw` into three files
   - Create `conductors.hw`, `insulators.hw`, `semiconductors.hw`
   - Update import paths in compiler

### Phase 3: Core Primitives

1. **Create `primitives/units.hw`**
   - Define fundamental SI units
   - Implement unit conversions
   - Test with simple calculations

2. **Test unit system**
   - Verify unit parsing
   - Test unit arithmetic
   - Validate error messages

### Phase 4: Logic Library

1. **Create `logic/gates.hw`**
   - Implement basic gates (AND, OR, XOR, NOT)

2. **Create `logic/arithmetic.hw`**

3. **Stress test the compiler**

### Phase 5: Routing Patterns

1. **Create `routing/patterns.hw`**
   - Define trombone delay pattern

   - Verify geometric calculations

### Phase 6: Component Library

## 9. Best Practices for Stdlib Development

### Logical Grouping

**Group by Material/Process**: If I'm building a PCB, I only import `@std/materials/conductors`. I don't need `semiconductors.hw`.

**Group by Logical Complexity**: Keep logic gates in one file so the synthesizer has a fast "shopping list" when it unrolls your code.

### File Size Philosophy

**Large files are better** for this DSL. The compiler's Symbol Table is O(1). One `components.hw` file with 1,000 resistors is faster to resolve than 1,000 separate files.

### Naming Conventions

- **Materials**: PascalCase (Copper, Silicon, FR4)
- **Modules**: PascalCase (AndGate, RippleCarryAdder)
- **Units**: PascalCase (Meter, Volt, Ohm)
- **Properties**: snake_case (resistivity, band_gap)
- **Pins**: PascalCase (A, B, Out, Cin, Cout)

### Documentation Standards

Every stdlib file should start with:
```hw
## Standard Library v0.1.6 - [Category Name]
## [Brief description of what this file contains]
## [Optional: Sources, references, standards]
```

Every definition should have a `description:` property explaining its purpose.

## 10. Migration Path

### For Existing Code

1. **Materials**: Update import paths from `@std/materials` to `@std/materials/conductors` (or appropriate category)
2. **Syntax**: No changes needed - materials already use v0.1.6 syntax
3. **Performance**: Expect faster compilation due to better organization

### For New Code

1. **Import only what you need**: `import @std/materials/conductors` instead of importing everything
2. **Use stdlib modules**: Reference `@std/logic/gates.AndGate` instead of defining your own
3. **Follow stdlib patterns**: Use the same style for your own libraries
